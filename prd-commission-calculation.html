0. 产品经理想法与业务逻辑（PM专属导读）

我为什么要制定这套算钱的规则？

因为我们的底层账户架构是“全 MT5 体系”（每个客户既有佣金账户，又有交易账户）。如果在算销售提成时，只是简单地把所有账户的入金加起来，会引发灾难性的“左脚踩右脚”刷单漏洞。比如：平台发了 1000 块佣金给客户，客户把这 1000 块转到交易账户，如果不做过滤，系统就会误以为客户又“真实入金”了 1000 块，销售又能跟着拿提成，这会导致平台资金无限流失。

这套规范的核心逻辑是什么？

  • “大钱包”抵消法： 我们不再看单个账户的流水，而是把一个客户名下的所有账户当成一个“大钱包”。左口袋（佣金账户）转到右口袋（交易账户），在大钱包的层面看，总资金没变。所以我们在计算时，要求研发直接在底层把“内部互转”的记录全部删掉，只算真正从外面充进来的钱。
  • 自客同享： 销售自己往往也是平台的交易客户。他自己充的钱、交易的手数，也必须算进他自己的业绩里拿提成。
  • 搭积木架构（防性能崩溃）： 因为我们需要支持按日（测试用）、按月（主营业务发钱）、按季、按年计算。为了防止月底算账时系统去查海量流水导致崩溃，我要求系统每天凌晨偷偷跑个“日切片账单”存起来。到了月底，直接把 30 张日账单加起来发钱就行了。
PM 总结： 这份文档就是为了让研发写出“绝对防刷”的代码，让测试知道怎么去“造最恶心的互转数据”来验证系统漏洞。

1. 核心痛点与防刷单漏洞预警（为什么我们要这么做）

我们采用“全 MT5 账户体系（Wallet in MT5）”。即系统中没有独立于 MT5 之外的资金钱包，客户的佣金账户和交易账户均开设在 MT5 底层。

必须防范的底层漏洞（研发必读）：

  • 防漏洞 1：内转导致“累计出入金暴增”：如果客户真实充值 1 万，然后在自己的佣金账户和多个交易账户之间频繁互转 10 次。若系统不剔除内转记录，该客户当月的“累计入金”会暴增至 10 万，“累计出金”也会暴增至 10 万。这会直接导致销售利用“累计入金”指标套取高额提成。
  • 防漏洞 2：平台发钱导致“无限套娃”：平台给销售发放了 1000 美金提成（打入佣金账户），销售将其转入交易账户。如果系统不拦截系统发放标识，这 1000 美金又会变成该销售当月新增的“入金业绩”，下个月又会据此发提成。

2. 研发执行标准：内转计算逻辑与出入金公式

研发数据过滤与聚合规则（必须拆分现金与内转）

在计算客户业绩时，虽然以 `User ID`（CRM 客户标识）为维度进行大资金池聚合，但必须在底层严格区分“现金流水”和“内转流水”。因为内转也是入金的一种形式，需要被记录在报表中，但绝不能用来发提成。

// 研发必须在底层查询时对流水进行打标分类：
IF comment LIKE '%Internal Transfer%' THEN Type = '内转' // 计入累计内转，不发钱
ELSE IF comment NOT LIKE '%Commission%' AND comment NOT LIKE '%Bonus%' THEN Type = '现金' // 计入累计现金，用来发钱
ELSE DROP // 拦截平台发钱，彻底丢弃，防套娃

【出入金与净入金】计算公式：

1. 累计现金入金 / 出金： 只统计真正走支付通道进出的外部资金。 报表展示 + 提成基数
2. 累计内转入金 / 出金： 统计佣金账户与交易账户互转的内部资金。 仅作报表展示
有效净入金 (发提成唯一指标) = SUM(累计现金入金) - SUM(累计现金出金)

注：累计内转入金和出金，在“大钱包”层面相互抵消，绝对不允许参与“有效净入金”的计算！

3. 测试执行标准：对账沙盘推演

测试团队必须按照以下沙盘逻辑，在测试环境中制造极端数据，并断言最终的日结/月结账单。

测试用例 1：内转与平台发钱不入账（断言净入金与累计量）

测试造数据：

  1. 客户 A 通过微信向 [佣金账户] 充值 $1,000。
  2. 客户 A 将 $1,000 从 [佣金账户] 内转至 [交易账户]。
  3. 平台向客户 A（如果他也是销售）发放提成 $500，随后客户 A 将其转入 [交易账户]。

系统必须输出（断言）：

  • 累计现金入金：$1,000
  • 累计内转入金：$1,000（不可与现金混淆导致暴增至 $2,000）
  • 累计现金出金：$0
  • 最终有效净入金必须等于：$1,000
测试用例 2：新销售注册时间边界（时区与起算点断言）

测试造数据：

  1. 造一个新销售，绝对注册时间转换为 MT5 时间后恰好为 11月15日 14:30:00。
  2. 在 14:29:59 为其名下客户造一笔 $10,000 入金。
  3. 在 14:30:01 为其名下客户造一笔 $5,000 入金。

系统必须输出（断言）：

  • 11月15日的日结账单中，净入金必须等于：$5,000
  • $10,000 必须被丢弃（因为发生在注册前一秒）。
测试用例 3：搭积木快照聚合（防重查流水断言）

测试造数据：

  1. 系统已正常跑完 11月1日 至 11月30日 的所有日结账单。
  2. 测试人员在数据库中，手动将 11月15日 的《日结账单》净入金强行从 $1,000 修改为 $5,000。
  3. 触发 12月1日凌晨的“月结跑批”任务。

系统必须输出（断言）：

  • 11月的《月结汇总单》总入金，必须比修改前多出 $4,000。
  • 核心断言：月结跑批时，系统日志中绝对不能出现连接 MT5 数据库查询历史流水的 SQL。
测试用例 4：销售自客业绩同享（自交易断言）

测试造数据：

  1. 销售 A 邀请了直客 B。
  2. 直客 B 当月净入金 $10,000，交易 50 手。
  3. 销售 A 用自己的 [交易账户] 净入金 $2,000，交易 10 手。

系统必须输出（断言）：

  • 销售 A 的当月总入金业绩必须为：$12,000
  • 销售 A 的当月总交易量业绩必须为：60 手
  • （即：本人数据必须被完美纳入提成基数）

! 提成派发核算模式（三种提成计算场景）

模式互斥声明（单选规则）

系统后台配置奖励规则时，以下三种计算方式为严格单选互斥（只能选其一）。同一条奖励规则绝对不能同时应用多种计算模式，以彻底防范“同一笔入金在不同维度被多次结算”的双重计费漏洞。

系统必须支持以下三种不同的提成核算模式，以满足不同代理线和销售团队的考核规则：

模式一：按单个用户独立计算（不抵消）

场景：高净值单客奖励

逻辑： 独立计算每个直客的净入金。只要客户 A 的净入金达标，就给销售发客户 A 的提成。客户 B 哪怕大额亏损出金，也不影响客户 A 带来的奖励。

风控预警： 极易发生“黑市对敲刷单”（用B出金的钱垫资给A入金套利），建议仅用于严控的大客户渠道。

模式二：按销售伞下全员汇总（抵消大资金池）

场景：标准销售月度考核

逻辑： 销售当期总业绩 = SUM(伞下所有客户当期入金) - SUM(伞下所有客户当期出金)。客户 A 的入金必须填平客户 B 的出金后，如果有正向结余，销售才能拿提成。

风控优势： 彻底杜绝对敲套利，倒逼销售维护全局资金盘。

模式三：按分组/代理条线汇总

场景：团队/机构代理结算

逻辑： 突破单个销售的界限，以一个“代理组”或整条“代理树”为一个大资金池进行抵消计算。用于计算团队总监管理奖或机构代理的总返佣。

业务红线：销售自客数据同等享受奖励

无论采用上述哪种模式，销售本人的 User ID 必须视为其伞下的第一个有效客户。销售自己名下交易账户产生的“有效净入金”和“有效交易量”，必须与旗下其他普通用户的数据一并汇总（或单独计算），同等享受业绩提成和奖励。

4. 研发架构标准：多周期独立核算（搭积木架构）

尽管业务上周期是“单选”的（主要按月），但在底层系统架构上，为了支持日结验收测试，且防止未来长周期直接查流水导致数据库崩溃，系统必须采用“底层切片，向上聚合”的搭积木架构。

提成结算底层数据流转图

Step 1: 每日打底座（单日基础业绩单）

每天 MT5 Server Time 00:05，系统自动抓取昨日一整天（00:00:00 - 23:59:59）的流水，计算出每个 User ID 昨日的【有效净入金】和【有效交易量】，生成一条不可变的日账单记录存入数据库。

触发动作：如果配置了“按日”规则（如UAT测试），则依此切片进行日结派发。
Step 2: 主营月结向上搭积木（月度汇总业绩单）

到了月底最后一天 23:59:59（MT5时间），系统不再去 MT5 查流水，而是直接在数据库里把本月生成的 28~31 张【单日基础业绩单】进行 SUM 汇总求和，生成月度账单。

触发动作：这是生产环境 99% 的触发场景，依此汇总单进行月结提成派发。

5. 研发与测试基准：结算周期定义与时区红线

全局时区处理红线（严防对账错位）

在所有的业绩考核和提成计算中，世界里只有一种时间，那就是 MT5 Server Time。为了规避夏冬令时带来的灾难，研发必须遵守以下时区转换规范：

  • 底层存储：所有业务时间（如销售注册时间）在数据库底层统一存储为绝对的 UTC 时间戳。
  • 查询转换：在跑批执行 SQL 前，必须通过标准的 Timezone 库，将 UTC 转换为 MT5 当下所在时区的当地时间。
  • 绝对禁止：严禁在后端业务代码中使用 Local Time，严禁使用硬编码的 +6h 或 +8h 来处理时间偏移。
